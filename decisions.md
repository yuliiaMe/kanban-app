# Архітектурні рішення (Decisions)

## 1. Авторизація (OAuth)
- **Вибір провайдерів**: Вирішено підтримувати Google OAuth (обов'язково) та Facebook OAuth. 
- **Ідентифікація користувача**: Користувач ідентифікується за полем `email`. 
- **Логіка об'єднання акаунтів (Account Linking)**: Якщо людина вперше зареєструвалась через Google з певною поштою, а потім залогінилась через Facebook до якого прив'язана та сама пошта, система повинна розпізнати, що це один і той самий користувач (перевірка за унікальним індексом `email` у базі даних). Новий запис не створюється, натомість до існуючого користувача додається інформація про новий метод авторизації (provider id).
- **Непідтверджені email-и**: Користувачі з непідтвердженими email-ами відхиляються на рівні бази даних та UI (особливо актуально для Facebook), щоб уникнути захоплення акаунтів та підробки особистості.
- **Токен сесії**: Використовуються JWT (JSON Web Tokens). Це дозволяє мати безпечну stateless авторизацію, де токени валідуються на бекенді без потреби зберігати активні сесії в базі даних.

## 2. База даних та Real-time синхронізація
- **Вибір технології**: На даному етапі використовується mock-клієнтська реалізація (UI), оскільки інтеграцію з хмарними сервісами (Firebase) було скасовано. Надалі планується реалізація кастомного бекенду (наприклад, Node.js + Socket.io) або підключення іншої БД.
- **Чому**: Це дозволяє швидко прототипувати інтерфейс та функціонал без прив'язки до конкретного BaaS-провайдера.
